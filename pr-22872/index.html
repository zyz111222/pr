瓶颈根因：权重 all_gather_weights() 在全局 KV/Compressor/Indexer 缓存更新之后才发射，仅靠短促的 Local Attention 无法掩盖 HCCL 通信时延，产生大量串行气泡。

优化点 1

提前发起 O-Proj 权重异步 AllGather，彻底掩盖通信气泡

vllm_ascend/attention/context_parallel/dsa_cp.py (+4 / -4)

在 DeepSeek-V4 PCP (Prefill Context Parallelism) 开启 O-Proj 权重分片（_parallel_o_proj）时，每层 Attention 完成后需要通过 all_gather_weights() 在独立通信流上拉齐完整的 O-Proj 权重矩阵。修改前，该异步集合通信被放在 _prepare_caches_and_query() 的末尾（所有全局 SWA / Compressor / Indexer KV Cache 更新全部完成后才启动），导致剩余 Local Attention 的计算窗口不足以覆盖权重 AllGather 时延，主流在进入 _forward_o_proj() 前产生长达 125.8 ms（131K 全模型累计）的串行等待气泡。

将仅 4 行代码从 Global Cache 循环之后上移至 _gather_and_restore_hidden_states() 之后，使 all_gather_weights() 与缓存更新及本地注意力完全重叠。

修改前为何存在气泡？

原逻辑需等待 SWA、Compressor（compress_ratio > 1）、Indexer（compress_ratio == 4）三组全局缓存全部更新完毕后，才发起权重 AllGather。此时仅剩 Local Attention 阶段可用来掩盖，通信长尾直接顶出到主计算流。

为何提前发射绝对安全？

_parallel_o_proj.all_gather_weights() 仅读取静态模型权重分片，不依赖任何 KV Cache、Compressor 或 Indexer 输出，也没有与 hidden_states 聚合产生数据依赖冲突。

空分片 SPMD 一致性保证

即使某个 PCP Rank 本地没有有效 Token（提前跳过 Local Attention），它依然执行了 _gather_and_restore_hidden_states() 后的权重聚合，确保全卡集合通信序列严格对齐（已在 test_dsa_cp.py 与 test_dsa_v1.py 中断言）。

优化点 2

消除 o_proj_input 冗余分配与零拷贝直通

vllm_ascend/attention/dsa_v1.py (+12 / -2)

在 AscendDSAImpl.forward() 中，原实现无论是否存在 Padding Token，都会在进入 Attention 前预先执行 o_proj_input = hidden_states.new_zeros(o_proj_input_shape)，随后再把 _forward_attention() 的返回值通过切片赋值 o_proj_input[:actual_tokens] = ... 搬运进去。在 DeepSeek-V4 单步 Prefill 中，这会额外触发 301 次 ZerosLike + 301 次 TensorMove（共 602 个冗余 Kernel），把完整的 Attention 输出在 HBM 中多读写一整遍，造成 95.5 ms 纯访存浪费。

当 actual_tokens == o_proj_input_shape[0] 且张量形状、dtype、连续性完全一致时，直接传递 attn_out 引用，消除 301 × ZerosLike 与 301 × TensorMove。

快路径为何对 Prefill 几乎 100% 命中？

在长序列 Prefill 场景中，actual_tokens 通常与 o_proj_input_shape[0] 相等（无额外 Decode padding），且 _forward_attention() 输出天然是 bfloat16 连续张量，因此直接复用 attn_out 对象（mock_o_proj.call_args.args[0] is attn_out），零显存分配、零数据搬运。

空 Token 分片与 Padding 场景如何兜底？

当 actual_tokens == 0 且开启 enable_pcp_o_proj_weight_sharding 时，在早返回分支内才惰性执行 hidden_states.new_zeros(o_proj_input_shape) 以安全参与 OTP/PCP 集合通信；若存在尾块 Padding 或非连续视图，则自动落入 else 分支保持行为 100% 等价。

优化点 3

MoE PCP 通信前 MXFP8 (CEIL) 预量化 + 本地 TopK + 3 路原生 AllGather

prepare_finalize.py · routed_experts.py · fused_topk_router.py

在 PCP=4 架构下，MoE 层的 PrepareAndFinalizeWithAllGather 需要把各卡持有的 N/4 个 Token 聚合为全量 N 个 Token 再送入专家计算。修改前存在三重放大浪费：① 激活以 BF16 (2 B/elem) 全精度通信；② Router 传输完整 [N, E] 维 Logits 并额外调用 all_gather_input_ids；③ 4 张 NPU 卡在聚合后各自重复对全部 N 个 Token 执行一遍 TopK 路由和 MXFP8 动态量化。

基于 950DT 单机四方案消融实验，本 PR 最终收敛为 Variant B 并与刚合入主干的 #22230（W8A8 / W8A8MXFP 预量化）无缝整合：在 PCP AllGather 之前，每张卡仅对自己拥有的 N/4 本地 Token 完成 MXFP8 (DynamicMXQuantScaleAlg.CEIL) 预量化与本地 TopK 路由，随后直接发起 3 路原生 HCCL pcp_group.all_gather（无 ConcatD/Slice 字节打包开销），既将激活通信量砍掉 ~48.4%（2 B → 1 + 1/32 = 1.03125 B），又将 TopK 与量化算力降至 1/4。

每张 PCP 卡仅对本地 N/4 Token 做预量化和路由，随后通过 3 路原生 HCCL AllGather 汇总；通信带宽减半且免除了 ConcatD/Slice 打包拷贝。

通信量为何净省 ~48.4%？

每个元素由 BF16 (2 B) 转为 FP8 E4M3 (1 B)，外加每 32 个元素共享 1 字节的 E8M0 block scale（1/32 = 0.03125 B/elem），总激活通信量从 2 B 降至 1.03125 B（-48.44%）；同时 Router 通信从 E 维浮点缩减为 2 × top_k 维 int32。

15 项严密 Guard 确保零副作用

_can_pre_route_pcp() 逐一校验：硬件支持 DYNAMIC_MX_QUANT_SCALE_ALG_ONE、dp_size==1 & tp_size==1、非 Graph 捕获、非强制均衡 / EPLB / 混合部署、严格匹配 AscendFusedTopKRouter + sqrtsoftplus + 无视觉偏置 bias_vl + 非 producer。任一不满足自动无缝回退。

与 #22230 的架构协同

在 Rebase 到 a34bd911c 后，将 W8A8、W8A8MXFP 与 W4A8MXFP 统一收口至 _supports_pcp_quant_prepare() 与 PrepareAndFinalizeWithAllGather.prepare()，彻底避免了重复代码并覆盖完整回归单测。
